Private AI agent

A personal assistant that runs AI locally, understands context from Pulse, Ascend, and future apps, and helps me manage everyday life while keeping my data on hardware I control.

  • Python
  • llama.cpp
  • SQLite
  • Linux
  • Docker
  • WireGuard

proposed stack · hardware pending

problem
My apps can hold useful pieces of my life, but I want an assistant that can connect that context and help me act on it, without depending on cloud AI processing.
approach
Run the model and personal context locally, with limited, permissioned access to my apps and approval before it makes changes. The goal is offline operation at home, plus access from away through a private encrypted connection when a network is available.
challenge
Enough local compute for useful offline AI. Model quality, response time, and memory requirements need to be tested before choosing a powerful enough machine.
next
Benchmark local models and size the hardware, then prototype read-only context from my apps before adding actions or remote access.

Home server & automation

A NAS home server and local home automation setup, with a longer-term goal of connecting both to my private AI agent.

  • Linux
  • OpenZFS
  • Samba
  • Home Assistant
  • MQTT

proposed stack · hardware pending

problem
I want a home base for files, backups, and everyday automation, with room to connect those services to the personal apps and assistant I'm building.
approach
Build the NAS and home automation services first, with local control and recoverable backups. Keep them useful on their own, then add a permissioned connection to the offline agent.
challenge
Hardware capacity for the wider setup. The eventual offline AI workload needs substantial local compute, alongside storage and always-on home services. Memory, power use, noise, and keeping those services responsive will shape the build.
next
Size the storage and compute requirements, validate backup recovery, and start with a small set of local automations before integrating the agent.

tf-access-map

A read-only dashboard I built for myself to untangle a large access problem: who can change what across a Terraform Cloud estate, how they got that access, and whether the platform is healthy right now.

  • Python
  • HCP Terraform API
  • GitLab API
  • Microsoft Graph
  • Kubernetes
  • HTML / CSS / JS

case study →built for my own use

problem
I had to work out, across thousands of workspaces and hundreds of teams, "who can apply to this, or read its state, and how?" Access chained through SSO groups, teams, projects, and org-wide permissions, and some of it was never written in code. By hand, that was weeks of clicking through a UI.
approach
Read-only collectors with an endpoint allowlist snapshot Terraform Cloud, Git, the identity provider, and the agents' Kubernetes pods, using my own login. A model turns the snapshot into an access graph, and a strict HCL evaluator finds where each grant is declared. One static page shows it all, with no server to run.
outcome
Weeks of manual auditing done in days. Its first run matched the manual numbers exactly. Surfaced access granted outside code, teams that can read all state, and auto-apply workspaces with unprotected deploy branches. Zero writes, no stored tokens, 150+ tests.
